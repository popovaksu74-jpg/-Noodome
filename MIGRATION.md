## 1. Из чего состоит проект и что привязано к аккаунтам

| Часть | Что это | Где живёт сейчас | Что привязано к аккаунту |
|---|---|---|---|
| Сервис для команды | `index.html` | GitHub Pages | Адрес сайта (`ИМЯ.github.io/репозиторий`) |
| Страница-приглашение | `p.html` | GitHub Pages | Тот же адрес. Он **зашит в ссылки, которые вы разослали участникам** |
| Адрес хранилища | `config.json` | GitHub | Адрес вашего Apps Script |
| Хранилище | `backend/Code.gs` | Google Apps Script | Google-аккаунт владельца: таблица, папка на Диске, пароль `TEAM_TOKEN` |
| Заявки, список, журнал | Google-таблица | Google-аккаунт владельца | Владелец таблицы |
| Приглашения и общие блоки | Файлы JSON | Папка на Google Диске | Владелец папки |
| Ключ ИИ и пароль команды | Браузер сотрудника | У каждого свой | Только его браузер |
| Исходный код | Папка `src/` | GitHub | Ничего |

Главное, что нужно запомнить:
- **Всё содержимое проекта лежит в двух местах**: репозиторий GitHub и Google-аккаунт владельца. Перенос сводится к тому, чтобы повторить их у нового владельца.
- **Участники пользуются ссылкой вида `https://АДРЕС/p.html?ref=имя`.** Адрес `АДРЕС` это домен GitHub Pages. Если он изменится, разосланные ссылки перестанут работать. Поэтому для рабочей версии сразу заведите **свой домен** (см. раздел 3).
- **Адрес хранилища лежит в `config.json`.** Его можно менять, не трогая ссылки участников: страница сама подхватит новый адрес.

## 2. Чек-лист перед запуском в работу

Учебная версия содержит то, что нельзя переносить в рабочую как есть.

**Содержимое**
- [ ] Удалить пример Михаила Тихомирова из `src/data/mikhail-tikhomirov.seed.json` (там интервью и портрет реального человека) или заменить вымышленным. Пересобрать `index.html`.
- [ ] Удалить из репозитория `i/mikhail-tikhomirov.html`.
- [ ] В `config.json` удалить строки `"prototype"` и `"example"`. Тогда страница по несуществующей ссылке покажет обычное сообщение «Приглашение не найдено», а не пояснение про учебный прототип и ссылку на пример.
- [ ] Проверить права на все материалы. Тексты, фото пространства, портреты амбассадоров, иллюстрации афиши и подвал взяты с noodome.club и из презентации клуба для учебного показа. Для рабочей версии нужно разрешение клуба или собственные материалы.
- [ ] Подтвердить у амбассадоров, что они согласны на показ имени, роли и портрета.
- [ ] Заменить шрифт-заменитель Cormorant Garamond на фирменный Wremena, если у клуба есть на него лицензия для веба.
- [ ] Проверить, что реквизиты в подвале и в `CLUB` в начале `src/landing.js` актуальны (адрес, телефон, почта, соцсети, ссылки на документы).
- [ ] Заменить афишу в `src/data/club.json` на актуальные события или оставить примеры и договориться, что актуальное высылают лично.

**Данные и право**
- [ ] Выяснить у юриста клуба требования к заявкам. Заявка содержит имя и контакт кандидата, это персональные данные. Нужно решить, нужны ли на форме согласие на обработку и ссылка на политику конфиденциальности, и где разрешено хранить данные. Закон может требовать, чтобы первичное хранение персональных данных граждан РФ было на территории России. Google-таблица этому может не отвечать. Если так, см. раздел 5.
- [ ] Решить, кто отвечает за данные, кто имеет доступ и как долго хранятся заявки.
- [ ] Заменить текст в форме и в подвале, если юрист потребует.

**Техника**
- [ ] Разделить среды: учебную (для показа) и рабочую (для настоящих данных) держать отдельно, с разными таблицами, разными паролями и разными репозиториями. Подробнее в разделе 8.
- [ ] Создать рабочий аккаунт или группу владельцев, а не личный аккаунт одного человека. Иначе при уходе сотрудника проект останется без владельца.
- [ ] Придумать резервное копирование (см. раздел 7).

## 3. Перенос на другой аккаунт GitHub

Выберите вариант в зависимости от того, нужно ли сохранить историю изменений.

### Вариант A: передать репозиторий целиком (сохраняется история)
1. В репозитории: **Settings → General → внизу Danger Zone → Transfer ownership**.
2. Введите имя нового владельца (аккаунт или организации), подтвердите.
3. Новый владелец принимает передачу по письму от GitHub.
4. После передачи заново включите Pages: **Settings → Pages → Deploy from a branch → main / root → Save**.
5. Адрес сайта изменится на `НОВОЕ-ИМЯ.github.io/репозиторий`. GitHub какое-то время перенаправляет старые адреса репозитория, но **адреса Pages не перенаправляются**. Ссылки участников сломаются, пока вы не сделаете шаг из раздела «Не потерять ссылки».

### Вариант B: новый репозиторий с копией кода (чистая история)
1. Скачайте код: на странице репозитория **Code → Download ZIP** и распакуйте. Или командой:
   ```bash
   git clone https://github.com/СТАРЫЙ-ВЛАДЕЛЕЦ/СТАРЫЙ-РЕПОЗИТОРИЙ.git noodome
   ```
2. Войдите в новый аккаунт GitHub, создайте пустой репозиторий (**New repository**, без README).
3. Загрузите файлы: на странице пустого репозитория **uploading an existing file** и перетащите содержимое папки. Через git:
   ```bash
   cd noodome
   rm -rf .git
   git init -b main
   git add .
   git commit -m "Noôdome · Приглашения"
   git remote add origin https://github.com/НОВЫЙ-ВЛАДЕЛЕЦ/НОВЫЙ-РЕПОЗИТОРИЙ.git
   git push -u origin main
   ```
4. Включите Pages (см. выше).

### Свой домен: чтобы адрес никогда не менялся (рекомендуется для рабочей версии)
1. Выберите адрес: например, `invite.noodome.club`. Его создаёт тот, кто управляет доменом клуба.
2. В репозитории: **Settings → Pages → Custom domain** → впишите адрес → **Save**.
3. В настройках DNS домена добавьте запись типа **CNAME**: имя `invite`, значение `НОВЫЙ-ВЛАДЕЛЕЦ.github.io`.
4. Через 10–30 минут включите **Enforce HTTPS**.
5. С этого момента ссылки участников имеют вид `https://invite.noodome.club/p.html?ref=имя`. При любом будущем переносе вы просто перенаправляете домен на новый репозиторий, а ссылки не меняются.

### Не потерять ссылки, уже разосланные с адреса github.io
Оставьте старый репозиторий и замените в нём `p.html` на переадресацию. Вставьте вместо всего содержимого `p.html` в **старом** репозитории:
```html
<!doctype html><meta charset="utf-8"><meta name="robots" content="noindex">
<title>Переход…</title>
<script>location.replace("https://НОВЫЙ-АДРЕС/p.html" + location.search);</script>
<p>Страница переехала: <a href="https://НОВЫЙ-АДРЕС/">перейти</a></p>
```
Старый репозиторий должен остаться с включёнными Pages. Участники, открывшие старую ссылку, попадут на то же приглашение по новому адресу.

### После переноса проверьте
- [ ] Открывается сервис по новому адресу.
- [ ] В `config.json` стоит адрес хранилища.
- [ ] Ссылка `…/p.html?ref=…` для согласованного приглашения показывает страницу.
- [ ] Старые ссылки перенаправляются.

## 4. Перенос на другой аккаунт Google

Хранилище это таблица, папка на Диске и скрипт Apps Script. Надёжнее всего поставить новое хранилище с нуля в новом аккаунте и перенести данные. Так нет зависимости от прав доступа старого аккаунта.

### Шаг 1. Резервная копия из старого хранилища
1. Откройте сервис, подключённый к **старому** хранилищу. Нажмите **«Подключения»** и убедитесь, что адрес и пароль на месте.
2. Откройте раздел **«Приглашения»**, чтобы данные подтянулись.
3. Слева нажмите **«Сохранить всё в файл»**. Скачается `noodome-priglasheniya-ДАТА.json`: в нём все приглашения (с интервью и вопросами для проверки), общие блоки клуба.
4. Заявки не входят в этот файл. Они лежат в таблице: откройте старую таблицу, вкладку **«Заявки»**. Скопируйте её в новую таблицу: правый клик по вкладке → **«Копировать в» → «Существующая таблица»** (или скопируйте строки вручную). Вкладки **«Журнал»** при желании тоже.

### Шаг 2. Поставить хранилище в новом аккаунте
Войдите в **новый** Google-аккаунт и выполните разделы «3. Общее хранилище» из [README.md](README.md): таблица, Apps Script с кодом `backend/Code.gs`, пароль `TEAM_TOKEN`, функция `setup`, публикация веб-приложения. Скопируйте новый адрес, оканчивающийся на `/exec`.

Если вы перенесли вкладку «Заявки» из старой таблицы, не создавайте её заново: `setup` создаст только недостающие вкладки.

### Шаг 3. Переключить сервис на новый адрес
1. В репозитории откройте `config.json`, замените адрес на новый, **Commit changes**.
2. Сотрудники открывают сервис → **«Подключения»** → вписывают **новый** адрес (если там остался старый) и **новый пароль** → «Подключить и проверить».

### Шаг 4. Загрузить данные в новое хранилище
1. Подключившись к **новому** хранилищу, слева нажмите **«Открыть файл»** и выберите сохранённый `.json`.
2. Все приглашения и общие блоки загрузятся как новые. Проверьте раздел «Приглашения»: у каждого приглашения сохранился статус.
3. Откройте несколько ссылок `…/p.html?ref=…`. Согласованные приглашения должны открываться.

### Шаг 5. Выключить старое
Когда убедитесь, что всё работает, в старом Apps Script откройте **Развернуть → Управление развертываниями** и архивируйте развертывание. Старый пароль и старую таблицу удалите или заархивируйте по правилам клуба. Что в них осталось, решите вместе с юристом: там были персональные данные.

### Короткий путь: передать владение (быстрее, но менее надёжно)
Можно передать таблицу и папку данных новому аккаунту: **«Поделиться» → выбрать человека → «Владелец»**. Скрипт привязан к таблице и уйдёт вместе с ней. Но свойства скрипта (`TEAM_TOKEN`, номера папки и файла) придётся проверить заново, а развертывание веб-приложения может остаться привязанным к прежнему владельцу и перестать работать. Если выбрали этот путь, обязательно проверьте: откройте Apps Script новой таблицы, **Развернуть → Управление развертываниями**, убедитесь, что веб-приложение выполняется от имени нового владельца, при необходимости создайте новое развертывание и обновите `config.json`.

## 5. Другое хранилище вместо Google-таблицы

Сервис и страница-приглашение не привязаны к Google. Они общаются с хранилищем по простому HTTP-интерфейсу. Любой сервер, который его повторяет, подойдёт без переделки интерфейса: достаточно вписать его адрес в `config.json`.

### Когда это может понадобиться
- Данные кандидатов нужно хранить в России или в инфраструктуре клуба.
- Нужны личные аккаунты сотрудников, права доступа, история версий.
- Нужна связка с CRM без посредников.
- Объёмы выросли и лимиты Apps Script мешают.

Варианты: свой небольшой сервер (Node.js или Python с базой данных), облачные функции российского облака, Supabase или Firebase. Выбор делают вместе с тем, кто будет поддерживать систему.

### Контракт интерфейса
Адрес один. Запросы идут тремя способами.

**Публичные (без пароля)**

| Запрос | Что делает | Ответ |
|---|---|---|
| `GET АДРЕС?action=page&ref=КОД` | Отдаёт согласованное приглашение для страницы | `{"ok":true,"doc":{…}}` или `{"ok":false,"error":"not_found"}` |
| `POST АДРЕС` `{"action":"lead","name","contact","note","ref","page","utm","website"}` | Принимает заявку кандидата | `{"ok":true,"mode":"saved"}` |

`doc` в ответе содержит только публичные поля: `slug, name, nameGenitive, signoff, role, photo, photoIsPortrait, blocks` и `club` (данные общих блоков, которые использованы в `blocks`). **Приглашения в черновиках отдавать нельзя.** Поле `website` это ловушка для роботов: если оно заполнено, заявку надо молча проигнорировать. Нужен лимит частоты заявок.

**Для команды (с паролем)**: `POST АДРЕС` с телом `{"action":…, "token":"ПАРОЛЬ", "who":"Имя сотрудника", …}`

| `action` | Дополнительные поля | Ответ |
|---|---|---|
| `ping` | — | `{"ok":true,"who":"Имя"}` |
| `list` | — | `{"ok":true,"invites":[{slug,name,role,status,updatedAt,updatedBy,rev,leads,joined}],"club":{rev,updatedAt,updatedBy},"activity":[{at,who,action,what}]}` |
| `get` | `slug` | `{"ok":true,"doc":{…полный документ…}}` или `{"ok":false,"error":"not_found"}` |
| `save` | `doc`, `baseRev`, `link` | `{"ok":true,"rev","updatedAt","updatedBy"}` или `{"ok":true,"conflict":true,"rev","updatedBy","updatedAt"}` |
| `delete` | `slug` | `{"ok":true}` |
| `club` | — | `{"ok":true,"rev","data":{about,community,events,steps,apply}}` |
| `saveClub` | `data`, `baseRev` | как `save` |
| `leads` | — | `{"ok":true,"leads":[{row,createdAt,name,contact,note,connector,ref,status,comment,page}]}` |
| `setLead` | `row`, `contact`, `status` и/или `comment` | `{"ok":true}` |

Ошибки: `{"ok":false,"error":"текст"}`. Неверный пароль: `error: "auth"`.

### Правила, которые обязательно повторить
1. **Версии (`rev`).** Каждое сохранение принимается, только если `baseRev` равен текущей версии на сервере. Иначе ответ с `conflict:true`. Новое приглашение: `baseRev` 0 и такого `slug` ещё нет. Если `baseRev` > 0, а записи нет, это тоже конфликт с `deleted:true`. После успешного сохранения версия растёт на 1.
2. **Публично только `status === "approved"`.** Приглашение в статусе `draft` через `action=page` отдавать нельзя.
3. **Заявки без пароля**, но с защитой от спама и очисткой данных (в таблице нельзя оставлять значения, начинающиеся с `=`, `+`, `-`, `@`).
4. **Журнал.** Запись при создании, согласовании, правке (не чаще раза в 10 минут на приглашение и сотрудника), изменении общих блоков, смене статуса заявки.
5. **CORS.** Сервис вызывает хранилище из браузера с другого домена. Сервер должен отвечать заголовком `Access-Control-Allow-Origin` для адреса вашего сайта. Запросы POST идут с `Content-Type: text/plain;charset=utf-8`, поэтому предварительный запрос OPTIONS не посылается. Тело запроса это JSON-строка.
6. **Размер.** Документ может весить несколько мегабайт: фото лежат внутри в виде `data:`-строк.

Эталонная реализация: `backend/Code.gs`. Её можно читать как спецификацию.

### Как переключиться
1. Разверните новый сервер, проверьте все запросы (подойдёт `curl`).
2. Перенесите данные: в старом хранилище нажмите «Сохранить всё в файл», в новом нажмите «Открыть файл» (см. раздел 4).
3. Перенесите заявки: экспортируйте вкладку «Заявки» в CSV и загрузите в новую базу.
4. Поменяйте `backend` в `config.json`.
5. Сотрудники вписывают новый адрес и пароль в «Подключениях».

### Личные аккаунты вместо общего пароля
Сейчас единый пароль `TEAM_TOKEN`. Для рабочей версии лучше вход по аккаунту сотрудника: например, добавить на сервере проверку токена входа (OAuth) и поле `token` заменить на токен пользователя. Интерфейс сервиса при этом меняется только в одном месте: функция `api()` в `src/editor.src.html`.

### Связка с CRM
- Если CRM принимает вебхуки: в обработчике `lead` после сохранения заявки отправить её в CRM (в `Code.gs` это функция `submitLead_`, место для вызова `UrlFetchApp.fetch`).
- Если хранилище остаётся в Google: Zapier, Make или n8n с триггером «новая строка в таблице».
- Обратно, из CRM в сервис: через `setLead` можно менять статус заявки и комментарий.

## 6. Что менять в содержимом

| Что | Где |
|---|---|
| Адрес хранилища | `config.json` |
| Контакты, адрес, часы работы, соцсети, ссылки на документы, кнопки приложения, меню подвала | Начало `src/landing.js`, объект `CLUB` |
| Тексты и фото блоков «Что такое Noôdome», «Сообщество», афиша, «Как проходит знакомство», форма | Сервис → **«Клуб: общие блоки»** (правится без кода). Исходные значения для новых установок: `src/data/club.json` |
| Пример приглашения для новых установок | `src/data/mikhail-tikhomirov.seed.json` и вымышленный пример в `src/editor.src.html` (`var DEMO`) |

## 7. Безопасность и данные в рабочей версии

**Доступ**
- Пароль команды длинный, уникальный, хранится только в свойствах скрипта и у сотрудников в браузере. Не пересылайте его в чатах открытым текстом.
- При уходе сотрудника меняйте `TEAM_TOKEN`.
- Доступ к таблице и папке на Диске выдавайте только тем, кому нужно смотреть заявки напрямую.
- Лучше завести отдельный Google-аккаунт клуба для хранилища, а не личный.

**Данные**
- Заявки содержат имена и контакты. Определите срок хранения и правило удаления. Не пересылайте таблицу в мессенджерах.
- В файлах приглашений лежат исходные интервью: они не публикуются, но хранятся на Диске. Это тоже личные данные участников.
- Публичные страницы содержат только тексты и фото самого приглашения. Проверьте, что это то, на что согласился участник.

**Ключи ИИ**
- Каждый сотрудник использует свой ключ. Не вставляйте ключ в код и в репозиторий.
- Бесплатные тарифы ИИ-сервисов могут использовать тексты для обучения моделей. Для интервью с личными данными берите платный ключ с настройкой «не использовать для обучения» или не отправляйте лишнее.

**Резервные копии**
- Раз в неделю: **«Сохранить всё в файл»** в сервисе и копия таблицы (**Файл → Создать копию**). Файлы храните отдельно от репозитория.
- Google-таблица хранит историю версий: **Файл → История версий**.

**Лимиты**
- Apps Script ограничивает число запросов и время работы в сутки. Для десятков приглашений и сотен заявок в месяц лимитов хватает с запасом. Если трафик вырастет, смотрите раздел 5.

**Где хранить пароли и адреса.** Пароль команды, адрес хранилища и список тех, кому они выданы, храните в менеджере паролей или в закрытом файле вне репозитория. Не записывайте их в README, MIGRATION.md и другие файлы проекта: репозиторий публичный. Шаблон для записи лежит рядом с архивом: `ЛИЧНОЕ-ДОСТУПЫ-НЕ-ЗАГРУЖАТЬ-НА-GITHUB.txt`. В репозитории есть `.gitignore`, который не даёт случайно загрузить такие файлы и резервные копии `noodome-priglasheniya-*.json`.

## 8. Рекомендуемый порядок запуска в работу

1. **Сохранить учебную версию как есть.** Репозиторий и таблицу не трогать: по ним преподаватель и команда смотрят проект. Если нужно, архивируйте.
2. **Создать рабочие аккаунты:** организацию GitHub (или аккаунт клуба), Google-аккаунт клуба, домен для адреса.
3. **Решить вопросы из чек-листа** (раздел 2): права на материалы, согласия участников, персональные данные, где хранить заявки.
4. **Выбрать хранилище.** Если Google допустим, продолжать с разделом 4. Если нет, выбрать вариант из раздела 5.
5. **Создать новый репозиторий** из копии кода (раздел 3, вариант B), **без** примеров: удалить пример Михаила, `i/`, лишнее.
6. **Подключить домен** (раздел 3).
7. **Поставить рабочее хранилище** (README, раздел 3) и вписать адрес в `config.json`.
8. **Настроить общие блоки:** актуальные тексты, амбассадоры, афиша. Проверить реквизиты в подвале.
9. **Создать 1–2 тестовых приглашения**, согласовать с участниками, проверить ссылки на телефоне и отправку заявки до таблицы.
10. **Обучить команду:** сценарий демонстрации в README (раздел «Демонстрация за 5 минут»), правила согласования, работа с заявками.
11. **Рассылать ссылки.** Начать с нескольких участников, посмотреть, приходят ли заявки и как их обрабатывает команда, и только потом масштабировать.
12. **Подключить CRM** (раздел 5), когда процесс обработки заявок устоится.

## 9. Если что-то пошло не так

| Что происходит | Что делать |
|---|---|
| В «Подключениях» «Неверный пароль команды» | Пароль в свойстве `TEAM_TOKEN` не совпадает с введённым. Проверьте пробелы и регистр |
| «Нет связи с общим хранилищем» | Проверьте адрес `/exec`. Откройте его в браузере: должен показаться `{"ok":true,"service":"noodome-invites"}`. Если нет, развертывание не опубликовано или у него не стоит доступ «Все» |
| Ссылка на приглашение показывает «Приглашение не найдено» | Статус не «Согласовано» или код в адресе неверный |
| Ссылка показывает «Сервис пока не подключён» | В `config.json` пустой `backend` |
| Правки в Apps Script не действуют | Нужна новая версия развертывания: Развернуть → Управление развертываниями → карандаш → Новая версия |
| Две версии одного приглашения | Сервис покажет предупреждение о конфликте. Выберите «Взять версию коллеги» или «Сохранить мою поверх» |
| Сотрудник потерял данные в браузере | Если хранилище подключено, всё подтянется при подключении. Если нет, из файла «Сохранить всё в файл» |
| Что-то сломалось после правки кода | Верните прежнюю версию файла в GitHub (кнопка **History** у файла → **Revert**). В Apps Script версию можно вернуть в «Управление развертываниями» |
| Нужно очистить учебные данные перед рабочими | В «Приглашениях» удалите примеры, в таблице очистите «Заявки» и «Журнал» (кроме строки заголовков), удалите файлы в папке данных на Диске |
